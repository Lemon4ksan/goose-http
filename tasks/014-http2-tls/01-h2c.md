# 014.01: h2c with prior knowledge

Status: in-progress (started 2026-10-19). HPACK, the frames, and the h2c driver in
the epoll loop are on `main`, and pass h2spec on macOS and Linux; see "Handover" at
the end for what remains.

Task 014's phase 4: HTTP/2 over plaintext TCP, the client sending the connection
preface first (RFC 9113 §3.3), for HttpArena's baseline-h2c and json-h2c profiles on
port 8082 (goose-rest's task 047). It is h2 written in Goose
([decisions](../../docs/decisions.md#http2-is-modules-of-http-written-in-goose)), so
without TLS its cost is h2's alone.

## Built

- `hpack.goose` (`http.hpack`): HPACK, RFC 7541, as
  [architecture](../../docs/architecture.md#http2) describes.
- `h2frame.goose` (`http.h2frame`): each frame type of RFC 9113 §6 parsed and written,
  the preface, and the settings.
- Tests in `test/h2/`: `hpack` decodes every example of RFC 7541 Appendix C, checks
  the dynamic table's size after each block, and encodes C.4's and C.6's fields back to
  the RFC's bytes. `hpack_rules` round-trips every byte and 1,000 random strings
  through Huffman coding, refuses bad padding and EOS, refuses 10 malformed blocks
  (index 0 and past the table, integers past 2^31 - 1, truncated strings and lengths,
  size updates over the limit or after a field), drives 3,000 fields through an
  encoder and a decoder against a model of the table (eviction, entries larger than the
  table, a name from the dynamic table, the entries moving to the front), and checks an
  encoder's size updates and its three kinds of literal. `frames` round-trips every
  type, parses padding, priorities, the reserved bit, and an unknown type, splits a
  40,000-byte field block into CONTINUATIONs, asks for more at every prefix of a
  frame, and checks 25 frames that break RFC 9113's size and stream rules, each with
  its code and whether it ends the stream or the connection, and the settings' limits.

## Design for the loops

### Choosing h2c

A new `Config.h2c` makes a listener's connections HTTP/2 with prior knowledge: each
connection's first 24 bytes must be the preface (`h2_preface`), and anything else gets
a GOAWAY with PROTOCOL_ERROR and a close. HttpArena serves h2c on its own port, 8082,
and HTTP/1.1 on 8080. The alternative checks for the preface on every connection's
first bytes, which serves both on one port for one comparison per connection: no valid
HTTP/1.1 request starts with `PRI * HTTP/2.0`, whose version the HTTP/1.1 parser
refuses with 505 (question 1). Without TLS there is no ALPN to choose by, and the
`Upgrade: h2c` handshake is out of task 014's scope.

### State outside the slot

An HTTP/1.1 connection keeps today's slot (`EpollConn`, `RingConn`). An h2c connection
also owns an `H2Conn` in a worker-level `reusable` pool:

- both HPACK tables (9 KB each), its settings and the peer's, the connection's send
  and receive windows, the highest stream opened, and whether a GOAWAY went out;
- the partial frame: its header, and the bytes still to come;
- the field block being gathered from HEADERS and CONTINUATIONs, a run of the spill
  pool, with the stream it belongs to, as the CONTINUATION rule needs (§6.10);
- the streams it has open, as indexes into a second pool, and a round-robin ring of
  those with output and window.

Each open stream is an `H2Stream<S>` in that second pool: its identifier, its state
(§5.1), both windows, an `Exchange<S>` with the handler's state and `Stream`, and its
DATA waiting for window, as a run of the spill pool. The slot reaches its `H2Conn`
through an `i32` index, or, to leave the slot as it is, through a dictionary from slot
to index, a lookup per event on h2 connections only (question 3). An h2c connection
with one stream holds about 19 KB more than an HTTP/1.1 one, mostly the two tables.
`bench/run.sh`'s peak RSS checks that HTTP/1.1's is unchanged (task 014's criterion).

### Reading

The loop hands an h2c connection's received bytes to an h2 driver instead of
`answer`. The driver parses frames from the read buffer with `h2_parse`:

- DATA goes to its stream's handler as it arrives, without waiting for the whole
  frame, so the 8 KB read buffer (`Config.max_head`) holds any frame but a field block
  or a large SETTINGS or GOAWAY. Those are gathered in the spill pool, up to
  `SETTINGS_MAX_HEADER_LIST_SIZE` for a field block, which this side sets from
  `Config.max_head`, and 16,384 bytes for the rest.
- A whole field block is decoded with `hpack_decode` into the request the handler
  already takes: `:method` into `Request.method`, `:path` into `target`, `:authority`
  into a `Host` field, and the other fields as HTTP/1.1 field lines, so `field`,
  cookies, forms, auth, and media work unchanged. RFC 9113 §8.2 and §8.3's checks run
  as the fields go by: lowercase names, no connection-specific fields, `TE` only as
  `trailers`, pseudo-fields first and once, and the three a request needs. A
  `content-length` must match the DATA that follows (§8.1.1).
- Control frames are answered at once: SETTINGS with its ACK, PING with its echo,
  WINDOW_UPDATE into the windows, RST_STREAM by ending the stream with CLOSED, GOAWAY
  by refusing new streams. PRIORITY is parsed and ignored, and this side sends
  `SETTINGS_NO_RFC7540_PRIORITIES` (RFC 9218), since RFC 9113 deprecates priorities.
  PUSH_PROMISE from a client is a PROTOCOL_ERROR (§8.4).

### A handler's exchange on a stream

Each stream is one exchange, with its own state from `fresh`, called with the events
`answer` gives today:

- REQUEST, with `whole` set when END_STREAM came with the HEADERS, or the whole body
  arrived in the same read and fits in the read buffer, as HTTP/1.1's whole body does.
  Otherwise BODY for each DATA payload and END at END_STREAM. The trailers are a
  second field block (§8.1), passed in `Event.trailers`.
- Streams are concurrent, so a stream that waits (`later`) holds back no other, as a
  pipelined HTTP/1.1 request is held back today. Its DATA keeps arriving up to its
  window, and this side stops sending WINDOW_UPDATEs for it until the handler takes
  BODY again. `later`'s key gives its low 20 bits, the exchange's number today, to the
  stream's index in the stream pool, with a generation per stream, so `waits_for`
  finds the stream from the key (question 6).
- MORE is offered while the stream's queued DATA is below a threshold and its window
  is open, the h2 form of the write buffer's limit today.
- `http::upgrade` has no meaning in h2 (§8.6 forbids 101): on an h2 stream it is
  refused with 501. WebSocket over h2 is RFC 8441's extended CONNECT, which task 014
  leaves out.
- `send_file` reads the file in pieces with `pread` into DATA, the path files under
  64 KB take now, since frames need their headers and the windows between pieces.
- CLOSED comes at RST_STREAM, GOAWAY, or the connection's close, to every open stream.

### Responses

The handler writes its response with today's writers, into a buffer of its stream.
At `finish`, the driver turns the head into a HEADERS frame: the status from the
status line, each field lowercased, `Connection`, `Keep-Alive`, `Transfer-Encoding`,
and `Upgrade` dropped (§8.2.2), `Date` and `Server` from the worker's common fields.
The body becomes DATA. A response begun with `begin` takes a framing of its own
that, like an upgrade's `Framing.Raw`, writes `send`'s bytes as they are, and `end`
sets END_STREAM. This leaves the API and every HTTP/1.1 writer unchanged, for a parse
of a head the package just wrote. The other way is writers that emit HPACK
themselves when the `Reply` is h2, with no parse, and a check in each writer
(question 2).

### Output, flow control, and the scheduler

- HPACK encodes in the order the peer decodes, so a HEADERS frame and its
  CONTINUATIONs are encoded when they are written to the connection's output, never
  queued per stream. HEADERS isn't flow-controlled, and nothing may come between a
  HEADERS frame and its CONTINUATIONs (§6.10).
- Control frames and HEADERS go to the connection's output at once, ahead of DATA.
- DATA waits in its stream's queue for window. A stream with DATA queued and window
  left is on the connection's ring. The scheduler takes one frame from each stream on
  the ring in turn, the smallest of the peer's `SETTINGS_MAX_FRAME_SIZE`, the stream's
  window, and the connection's, until the output reaches `Config.write_buffer` on
  epoll or `Config.max_queued` on the completion loop, or the connection's window is
  spent. Round-robin needs no priorities; frames of one size keep streams fair.
- Send windows start at the peer's `SETTINGS_INITIAL_WINDOW_SIZE`, and a change of it
  moves every open stream's by the difference, below zero if need be (§6.9.2). A
  window past 2^31 - 1 is a FLOW_CONTROL_ERROR.
- Receive windows: this side advertises a stream window of
  `SETTINGS_INITIAL_WINDOW_SIZE` and raises the connection's with a WINDOW_UPDATE after
  its SETTINGS. A handler takes each BODY at once, so the driver gives the window back
  once half of it is used, for the stream and the connection, unless the stream waits.
  DATA past a window is a FLOW_CONTROL_ERROR.

### Limits and errors

- `SETTINGS_MAX_CONCURRENT_STREAMS`, from a new `Config` field; a stream past it gets
  RST_STREAM with REFUSED_STREAM. Its field block is still decoded, since the table
  must stay in step with the peer's, and then dropped.
- A connection error sends GOAWAY with the highest stream processed, then closes once
  it is written. A stream error sends RST_STREAM and goes on.
- Against floods: streams reset before their response is counted per connection
  (the 2023 rapid reset attack), a field block can't outgrow its limit through
  CONTINUATIONs, and PINGs and SETTINGS beyond a rate end the connection with
  ENHANCE_YOUR_CALM. The rates are to be set by measurement.
- Timeouts: the sweep's idle and write timeouts apply to the connection; a stream's
  `later` has its own timer, as an exchange's does.
- A stop sends GOAWAY with NO_ERROR, finishes the open streams, then closes, within
  `Config.grace_ms`.

### The loops

Everything above is Goose, in a driver both loops call; no shim changes, and
`http::serve` and `http::serve_epoll` keep their signatures.

| Loop | What changes |
|---|---|
| epoll (`epoll.goose`: epoll on Linux, kqueue on macOS) | The read path calls the h2 driver for an h2c connection. Output goes through the same write buffer, spill run (`EpollConn.out`), and `watch_out`. The scheduler runs again when the socket has room. kqueue needs nothing more, since its shim already presents epoll's events. |
| completion (`uring.goose`: io_uring, its emulation over epoll or kqueue, and IOCP on Windows) | Receives arrive in provided buffers as today, and the driver keeps partial frames in the spill pool. Sends go through `ring_send`, one in flight; the scheduler stops at `Config.max_queued` and runs again at the send's completion, where MORE is offered today. IOCP and the emulation share this Goose code and its shims, so they change with it. |

## Answers to the design's questions

Agreed 2026-10-19. The design decisions among them are in `docs/decisions.md`.

1. Each listener has its own mode, HTTP/1.1 or h2c with prior knowledge only, and one
   loop takes several listeners, rather than `http::run` once per port: HttpArena
   serves 8080 and 8082 from one container, and twice the threads on the same CPUs
   would distort it. TLS on 8081 and 8443 will need several listeners too.
2. Responses: the handler's HTTP/1.1 head is translated into HPACK, with no API change.
   Writers that write HPACK directly come only if a measurement shows the translation
   matters.
3. An `i32` in every connection slot points to its `H2Conn`. Task 014's memory
   criterion allows those 4 bytes per connection.
4. epoll first, since kqueue shares its code and macOS can test it; io_uring next, in
   a later run.
5. Defaults: `SETTINGS_MAX_CONCURRENT_STREAMS` 128, RFC 9113's default stream windows,
   and a larger connection window for uploads, to be tuned later. HttpArena's h2load
   runs with prior knowledge (`h2load -p h2c`) on port 8082: `-m 100` on baseline-h2c,
   at 256, 1,024, and 4,096 connections, and `-m 32` on json-h2c, at 1,024 and 4,096.
   Its validation uses `curl --http2-prior-knowledge`.
6. `later`'s key gives its low 20 bits to the stream's index in the pool.
7. A body that arrives over several reads comes as HTTP/1.1's does: the route chooses
   between gathering it whole and reading it in pieces.

Two more, agreed 2026-10-19, after the epoll loop was built:

8. The names stay as built: `Config.h2c`, `Config.listeners`, `Listener`, and
   `h2_max_streams`, `h2_stream_window`, and `h2_conn_window`
   ([decisions](../../docs/decisions.md#a-loop-takes-several-listeners-each-with-its-own-mode)).
9. The benchmark server serves h2c on its port + 2 by default, as HttpArena has 8082
   beside 8080, so HttpArena's Dockerfile needs no setting for it. `H2C_PORT` names
   another port, and `H2C_PORT=0` turns it off.

     writers (`message.goose`, `send` and `end`), so on h2 it now ends the connection
     with GOAWAY; RST_STREAM INTERNAL_ERROR on that stream alone would be enough.
   - A stream's body is gathered whole only within half the stream window, a limit
     `docs/api.md` states; with the default window (65,535) and `max_head` (8,192),
     `max_head` decides, as before.
   - h2spec on arm64 Linux isn't in `scripts/test.sh`; it's run by hand from an
     x86-64 container (`docs/development.md`, "Docker on macOS").

### Traps

- Goose keywords that look like names: `block`, `pad`, `in`.
- A thread may use only flat globals (spec §11.2): a global dictionary keyed by slices
  fails to compile from a `thread_fn`, hence `HPACK_NAMES`.
- A struct field holding a `u8[>..]&` can't be cleared: the checker assumes it may be
  the package's `reusable[]` pool `gathered`. So `h2_answer` takes its six scratch
  buffers as parameters.
- `bout`, the handler's buffer, is cleared after a call, not before: the checker can't
  tell an event's slices, read from the stream pool, from `bout`.
- `return f()` of a function with no value doesn't compile; write `f(); return;`.
- A nested function named like a std one (`find`) hides it for every call in scope.
- `&st.x.state` warns "redundant &" but is needed (`docs/goose-findings.md`).
- A stream that `later` makes wait must not get 500 before its timer starts: timers
  start after the calls (`start_waits`), as the HTTP/1.1 loops do.
- Streams closed during one call of `h2_answer` still count against
  `SETTINGS_MAX_CONCURRENT_STREAMS` (`closed_now`), since the client hasn't seen their
  end; h2spec 5.1.2 needs it. Streams the client reset don't count.
- The driver test's `session` reuses the stream pool, so a stream's pool index
  depends on the tests before it: look a stream up by its key or id, never assume an
  index.
- h2spec's `linux_amd64` binary is linked against glibc, so it doesn't run in an arm64
  container even with Rosetta; it needs an x86-64 container (`--network
  container:NAME` to reach the server).
- Another checkout's `scripts/test.sh` on the same Mac takes the ephemeral ports
  (`docs/known-issues.md`, "macOS"): `many` fails with `Can't assign requested address`
  on any loop. Check `netstat -an -p tcp | grep -c TIME_WAIT` before a suite.
- `bench/run.sh` needs `build/bench/` from `bench/build.sh`; `ONLY=goose` builds just
  the Goose servers and helpers. Copy a `main` build in as `goose-main` to compare: any
  server named `goose*` runs as the Goose server.

### Commands

```sh
python3 test/run_tests.py h2                      # the h2 tests
LOOP=epoll scripts/build.sh && scripts/test-h2spec.sh   # h2spec; H2SPEC_ARGS=-S for strict
WORKERS=4 LOOP=epoll build/server http 8080        # h2c on 8082, the port + 2
curl --http2-prior-knowledge http://127.0.0.1:8082/plaintext
h2load -t 4 -c 256 -m 100 -n 4000000 http://127.0.0.1:8082/plaintext   # h2c by default
bench/hpack.sh
PORT=29380 scripts/test.sh    # a port of its own; check TIME_WAIT first (Traps)
```

lists ("Docker on macOS"), built fresh, and an export of the tree mounted at `/w`:

```sh
docker run --rm --security-opt seccomp=unconfined --ulimit nofile=65536:65536 \
    -v "$work:/w" -w /w IMAGE sh -c 'PORT=29380 scripts/test.sh'
```
